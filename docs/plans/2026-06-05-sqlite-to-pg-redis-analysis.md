**日期**: 2026-06-05
**分析范围**: 全部 44 个涉及数据库的文件，22 个迁移脚本，前端轮询与状态管理

## 2. 数据库层现状

### 连接模式
- 单例模式：`getDb()` 返回唯一 `better-sqlite3` 实例，`closeDb()` 清理
- WAL 模式 + `busy_timeout = 5000`
- `db` 对象从 `app.js` → `setupRouter(config, db, log)` → 每个路由工厂 → 每个服务函数
- 无 DI 容器，无中间件注入，纯参数传递

### 当前依赖
- `package.json` 中**无** `pg`、`postgres`、`redis`、`ioredis`
- 整个代码库零 Redis 引用

## 3. SQLite 特有语法清单

| 构造 | 出现次数 | 文件位置 | PG 等价写法 |
|------|----------|----------|-------------|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | 全部 18+ 表 | 迁移 SQL、schema 定义 | `SERIAL PRIMARY KEY` 或 `GENERATED BY DEFAULT AS IDENTITY` |
| `last_insert_rowid()` | 3 处 | `routes/videos.js`, `services/episodeStoryboardService.js`(×2) | `INSERT ... RETURNING id` |
| `INSERT OR IGNORE` | 8 处 | characterGenerationService, dramaImportService, dramaService, episodeStoryboardService, propService, storyboardService | `INSERT ... ON CONFLICT DO NOTHING` |
| `INSERT OR REPLACE` | 2 处 | imageClient.js, promptOverridesService.js | `INSERT ... ON CONFLICT(uk) DO UPDATE SET ...` |
| `PRAGMA table_info()` | 2 处 | migrate.js, libraryDedup.js | `information_schema.columns` |
| `datetime('now', '-5 minutes')` | 1 处 | services/videoService.js | `NOW() - INTERVAL '5 minutes'` |
| `result.changes` | 1 处 | dramaService.js 检查行数 `=== 0` | `result.rowCount` |
| `info.lastInsertRowid` | 多处 | 所有 insert 调用方 | `result.rows[0].id` |

## 4. 数据序列化差异

| 差异点 | SQLite 现状 | PG 行为 | 影响 |
|--------|------------|---------|------|
| 日期时间 | 全部存为 TEXT (ISO8601) | TIMESTAMPTZ 原生类型 | 可迁移时保留 TEXT 或转换类型 |
| 布尔值 | INTEGER 0/1 | BOOLEAN true/false | 检查 `=== 1` / `=== 0` 的代码需改为 `!!value` 或 `=== true` |
| JSON 列 | TEXT 存 JSON 字符串，代码手动 `JSON.parse()` | JSONB 类型，pg 驱动自动解析 | 现有 `JSON.parse()` 会双重解析报错，需检测并移除 |
| 整数主键 | 自增 ID | SERIAL 自增 | 行为一致 |

## 5. 查询复杂度分析

### JOIN 使用
共 **6 处 INNER JOIN**（无 LEFT/RIGHT JOIN、无 CTE、无窗口函数）：
- `dramaService.js` 3 处：episode_characters → characters，storyboard_props → props
- `framePromptService.js` 1 处：storyboards → episodes
- `storyboardService.js` 1 处：episodes → storyboards

### 事务
仅 **1 处显式事务**：`dramaImportService.js` 中 `db.transaction(() => {...})`

此处需特别注意：`better-sqlite3` 的事务是**同步的**（callback 模式），PG 需要 `BEGIN` / `COMMIT` / `ROLLBACK`（async）。

## 6. 迁移机制现状

**双层迁移架构**：
1. **SQL 文件迁移**（`migrations/*.sql`）：按文件名排序，`database.exec()` 逐文件执行
2. **programmatic 安全网**（`ensureColumns`）：每次启动通过 `PRAGMA table_info()` 检查缺失列，自动 `ALTER TABLE ADD COLUMN`

迁移文件清单（22 个）：
- `01_init.sql`：初始 18 表完整 schema
- `02`-`08`：各表追加列
- `09`-`10`：新建 library 表、prompt_overrides 表
- `11`-`22`：追加列 + 新建 ai_model_map、image_proxy_cache 等表

---

## 7. 同步→异步改造范围

所有 DB 调用都是同步的（`better-sqlite3` 特性），PG 客户端（`pg`）全部异步。

需改造的文件分布：
- **路由层**（18 个文件）：Express handler 改为 async + try-catch
- **服务层**（24 个文件）：函数改为 async，调用处加 await

Express 异步错误处理需引入 `express-async-errors` 或显式 try-catch 包围。

## 8. Redis 可解决的问题

### 8.1 消除前端轮询
前端现有 3 种轮询模式：

| 模式 | 位置 | 间隔 | 最大时长 | 优先级 |
|------|------|------|----------|--------|
| 任务状态轮询 | generationTaskStore.pollTask() | 2s | 15min | **高** |
| 角色/道具/场景提示词生成 | useCharacters.js / useProps.js / useScenes.js | 3s | 60s | 中 |
| 外观锚点提取 | useCharacters.js L607 | 3s | 60s | 低 |

Redis Pub/Sub + WebSocket 可替代所有轮询。

### 8.2 状态缓存
- `async_tasks` 查询结果缓存（TTL 3s）
- drama 元数据缓存（低频变更）
- 角色/场景/道具库列表缓存

## 9. 双数据源策略建议

推荐**渐进式迁移**路径：

```
Phase 1 — 基础设施
  ├── 添加依赖 (pg, ioredis, knex)
  ├── 定义统一 DB 接口 (src/db/interface.js)
  ├── SQLite 适配器 (保持同步，Promise.resolve 包装)
  └── PG 适配器 (异步)

Phase 2 — SQL 方言翻译
  ├── 替换 5 类 SQLite 特有语法
  ├── 重写 22 个迁移文件为 knex 格式
  └── 替换 PRAGMA → information_schema

Phase 3 — 数据迁移脚本
  ├── scripts/migrate-sqlite-to-pg.js
  └── 数据完整性验证

Phase 4 — 异步化改造
  ├── 42 个文件 async/await 改造
  ├── 引入 express-async-errors
  └── 逐模块回归测试

Phase 5 — Redis 集成
  ├── Redis 连接 + Pub/Sub
  ├── WebSocket 服务
  ├── 前端订阅替代轮询
  └── 降级回退（Redis 不可用时恢复轮询）

Phase 6 — 测试与并行运行
  ├── PG 测试套件
  ├── 双数据源对比验证
  └── 生产并行运行
```

## 11. 其他风险

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| SQLite TEXT 日期排序与 PG TIMESTAMPTZ 行为一致性 | 高 | 迁移后并行验证日期比较逻辑 |
| INTEGER 布尔值 → BOOLEAN 类型转换 | 中 | grep `=== 1` / `=== 0` 全部替换为 `Boolean()` |
| JSON TEXT 列的 `JSON.parse()` 双重解析 | 中 | 代码扫描后统一处理 |
| Express 异步错误未被 catch 导致进程崩溃 | 中 | `express-async-errors` + 全局错误中间件 |
| 事务行为差异（同步 callback vs async BEGIN/COMMIT） | 高 | dramaImportService 事务需专项审查 |
| `result.changes` vs `result.rowCount` | 低 | 逐处替换 |

## 12. 替代方案：不迁移

如果 SQLite 当前满足需求（单机场景、数据量 < 1GB、无高并发读取），迁移到 PostgreSQL 的实际收益有限。

**SQLite 够用的场景**：
- 单用户或小团队使用
- 数据量 < 500MB
- 无读写并发瓶颈
- 无需 PG 的 row-level security / 权限隔离

**Redis 可以独立引入**（不依赖 PG 迁移）：
- 即使不迁移数据库，Redis 仍可用于任务状态 Pub/Sub
- 在异步任务完成时直接 PUBLISH 消息
- 前端通过 WebSocket 接收，消除 2s 轮询
- 只需后端新增 Redis + WebSocket，不影响数据库层
